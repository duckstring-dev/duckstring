## Data viewer

- A merge table opens newest first, as its log: the rows written by recent Runs, then the rest of the table. Rows a
  later write replaced are grey, deleted rows red; hovering the row number says which. **[live]**
- The number-of-changes (`updates`) column is gone from that default view. A freshness window still shows the rows
  changed inside it, with their update counts, and clicking a merge row still opens its history. **[live]**
- An append table opens newest Run first. **[live]**
- The exact current state of a merge table is what a query of it reads (`SELECT * FROM pond.table`). **[live]**
- Paging is fast anywhere in a large table: on attention, a page 400M rows into a 1B-row append table takes 0.01 s
  (it took 23 s), and a page of a 575M-row merge table 0.2 to 0.6 s (it took 30 s to 3 minutes). **[live]**
- Sorting a table of more than 100M rows asks first ("Sort N rows?"), since a sort reads all of it. **[code]** (the
  dialog was checked in a browser on a small table only)
- A query running more than a second shows "Running… Cancel". Cancel stops it on the Catchment too, then offers Run
  again. **[live]** (browser, throwaway Catchment)
- On a phone: the top row wraps (the close button stays top right); the freshness window and SQL box fold behind one
  "Freshness & SQL" bar, closed by default, which notes when a window or custom query is set. Held landscape, the
  run panels fold behind a RUNS bar and the sidebar into a strip that opens when a Pond is selected. **[live]**
- The UI is served with caching headers, so a browser picks up a new UI on its next load. **[live]**

## Append tables

- In a Pond's working copy, an append table's name is now a view: over the rows still held locally, and over the
  published files for its older Runs. Reads see the whole history as before (Ripple SQL, conflict checks, recomputes).
  **[live]** (`wa_views.pageview`: 22M rows local, 1.12B rows through the view, matching the published count)
- After each publish, once the Runs held locally outgrow twice the compaction threshold
  (`DUCKSTRING_COMPACT_THRESHOLD`, 256 MiB by default), the oldest move out, leaving about one threshold. The same
  rule compacts a merge table. **[live]**
- A Pond that rebuilds its working copy brings back only the recent Runs. **[live]** (`wa_views` came back at 0.22 GB)
- An existing append table switches at its next write. **[live]**
- **The trap:** `duckdb_tables()` lists base tables only, so a check like `SELECT count(*) FROM duckdb_tables() WHERE
  table_name = 'x'` no longer finds an append table (a merge table's name was already a view). Use
  `information_schema.tables`, which lists both. **[live]** Six attention Ponds used the first form to decide where
  to resume, took themselves for new, and reloaded data they already had. `pond check` and a deploy now name each use
  of `duckdb_tables()` in a Pond's code. **[code]**
- Writing to an append table with your own SQL (`INSERT INTO`) no longer works: write through `append_table`. **[code]**

## Upgrading to 0.9

- `duckstring pond check [--fix]` names each use of a removed API with its replacement; `--fix` rewrites the ones whose
  replacement is certain. A deploy prints the same findings, and the Catchment checks every deployed Pond when it
  starts (shown per Pond on `/api/status` as `compat`). **[live]** (run over the attention Ponds 2026-11-21)
- Removed: `fail_on_conflict` on `append_table` and the builder's `.append()`, replaced by `on_conflict`
  (`"skip_check"`, `"keep_prior"`, `"fail"`). The mapping differs between the two methods (see CHANGELOG). **[code]**
- Changed meaning: `memory` (below). **[code]**
- Changed default: `immediate_retries = 1`. **[code]**
- New major lines publish integer sums as `BIGINT`, not `DOUBLE`; existing lines keep `DOUBLE`. **[code]**
- The `duckdb_tables()` trap above. **[live]**
- A Pond with its own `pyproject.toml` now runs on the Catchment's Duckstring after an upgrade, its environment
  rebuilt at its next start. **[live]**
- A redeploy while a Pond is busy: the Duck on the old version finishes only the Run in progress, and the Runs it
  hadn't started run on the new version. **[code]**

## Memory

- `@ripple(memory="6GB")`, or `[pond] memory` for every Ripple of the Pond (SQL Ripples and dbt models included), is
  what the Pond's Runs need, DuckDB and Python together. **[code]**
- On the Catchment's own machine, Pond Runs share a memory budget in slots (`DUCKSTRING_RUN_SLOTS`, default 4;
  `DUCKSTRING_MEMORY_BUDGET`, default 80% of memory less 2 GB). A Pond waits for the slots that cover its `memory`
  (one by default), and DuckDB's limit is all of them. Fewer slots for heavier Ponds is how concurrency is controlled.
  **[code]** (the slots themselves were measured on AWS in 0.7.1)
- A Run that runs out of memory is retried once with every slot, outside the failure budget. **[code]**
- Before 0.9, `memory` meant memory held outside DuckDB and was taken off DuckDB's limit. **[code]**

## Puddles on a dev Catchment

- `pond puddle deploy [SOURCE...] [--set S] [--from PROD [--live] [--as-at TIME]] [--force]` deploys a Puddle as the
  Source line on a dev Catchment, so the Ponds there read it as their Source. **[live]** (attention-dev, 2026-11-21)
- A copied Puddle holds its data on the dev Catchment; a live one reads production through the production
  Catchment's API at each Run, never in place. **[live]**
- `refresh now POND --rewind` runs the Ponds a Refresh reaches from the Puddles' starting point again;
  `--next-change`, `--next-run`, `--most-recent` and `--to` move the Puddles' positions. **[live]**
- A Source can deploy a Puddle of itself (`pond puddle deploy transactions`, run in `transactions`). **[code]**
- The CHANGELOG's "Puddles on a dev Catchment" section has the rest (conflicts, replacing, removing).

## Monitoring

- A Run that a later one overtook (Runs queued behind a long one) is `superseded`, not `failed`, and names the Run
  that did its work. **[live]**
- A Ripple's own error is kept when its Run gives up; before, "stuck: active Pond Run with no running Ripple" replaced
  it after 30 s. **[code]**
- Run reports: `duckstring runs POND --reports` shows each Run's beside it; the web UI's Run Detail shows the selected
  Run's own report and the upstream reports it read. **[code]** (attention's Ponds don't report, so not seen live)
- Repair: one runs at a time. If a step fails, running `control repair` again runs the failed steps again while the
  others carry on, and a Catchment restarted mid-repair carries it on. **[live]** for the restart; **[code]** for the
  retry.
- A Pond's freshness for an App: `pond.freshness()` gains `changed`, when each Source's data last changed. **[code]**

## Disk

- A DuckDB file never shrinks: deleted rows leave space it reuses but doesn't return. A Duck that opens a working copy
  of at least 64 MiB that is at least half free copies the live data into a new file first. **[live]** (`wa_views`:
  24.8 GB to 1.05 GB)
- Each Duck spills to its own directory, `{root}/tmp/{pond}_m{major}`. A process killed mid-query leaves its spill
  files behind until removed. **[live]** (40 GB of them filled the attention machine's disk during a repair)
- A Rebuild empties a Pond's working copy, including anything it kept only there (attention's `wa_stories` kept its
  paid embeddings there, and a repair re-embedded 385k titles for $1.27). Worth a sentence wherever Rebuild and repair
  are explained: keep anything costly to recompute where a rebuild won't throw it away. **[live]**

Facts:

- PostgreSQL: `duckstring install postgres` uses PGDG apt (Debian/Ubuntu, Debian's default cluster turned off),
  PGDG dnf (RHEL family), Homebrew (macOS); prints the download link elsewhere. Never sudo: run as root on Linux.
  **[live]** (macOS Homebrew 18.7; `python:3.13-slim` in Docker, PGDG 18.7, no cluster started)
- The Catchment finds the server through `DUCKSTRING_PG_BIN`, the path `duckstring install` recorded, the packages'
  own places, then the PATH. A managed cluster lives in `{root}/records/pg` (built-in C.UTF-8 locale on 17+),
  listens on 127.0.0.1 on a port chosen once, and sets aside 512 MB by default (`catchment records --memory`).
  **[code]**
- Each line's schema and role are `{name}_v{major}`; an App with Records needs a name of lower-case letters, digits
  and underscores. Unqualified tables are the line's own (the role's search path). Every line reads every line;
  Ponds read with `duckstring_ponds`. **[code]**, tested against a real PostgreSQL.
- Records are the catalog `records` in `/api/serve/query`, the pg wire and the viewer's SQL, read-only, for anyone
  authenticated. **[code]**
- Media routes: `GET /api/app-data` (lines), `GET .../{name}/{major}/media`, `GET|POST|DELETE
  .../media/file?path=` (POST and DELETE need full). Upload takes a raw body or a multipart `file`. **[code]**,
  viewer **[live]**
- `pond.media()` keeps its listing as an input state, so `added()`/`removed()` are relative to the Ripple's previous
  completed Run, surviving registry loss through the run stamp. **[code]**
- A trial line answers 403 below Manage access; a retired line's address 307s to the live major's same path; during a
  cutover every line of the App answers 503 with `Retry-After: 5`. **[code]**
- The migration copies Records with `pg_dump` through a scratch database (sequences, constraints, indexes, views,
  ownership kept) and Media file by file (real copies, not hardlinks: an App appending in place would change both).
  `[app] migrate` runs in the App's directory and environment, 600 s limit. **[code]**
- `catchment download`: `records/records.dump` in place of `records/pg`; a fresh managed cluster beside a dump makes
  the line roles and restores it. The state backup does the same and carries Media up to 256 MB. **[code]**, tested
- `[app] instances = N` (needs `state = "none"`): growth as in App scaling below (it replaced 4 in flight per
  instance and least-busy routing), a sticky cookie, memory per instance, idle stop per instance; the sidebar shows the count. **[code]**, tested under
  concurrent load (requests spread across instances, all writing the line's Records).
- A Pond on a Pool or cloud compute reads Records and Media through the Catchment's Duck channel; Media in an object
  store and an external PostgreSQL directly. **[code]**, tested with real Ducks told they're elsewhere.
- `records:` Spouts deliver into `{pond}_v{major}` in Records; Apps read it read-only. **[code]**, tested end to end.
- `catchment records --listen 0.0.0.0 [--host H] [--tls-cert C --tls-key K]`: TLS only from other machines
  (self-signed by default, fingerprint in `catchment records`), `--reader-url` for a BI tool. **[code]**, a plain
  connection from the LAN address refused and a TLS one accepted (measured on macOS).
- `catchment records move managed|postgres://... [--postgres-version N]` and `catchment media move
  local|s3://...`: downtime for Apps with Records (or Media) while the copy runs, verified before the switch, the
  old store deleted after. Also the way to upgrade a managed PostgreSQL's major (install the new one first with
  `duckstring install postgres --postgres-version N`). Suggest `catchment download` first. **[code]**, tested:
  managed to another server and back, a real 17 to 18 upgrade, a forced failure (nothing changed), Media to S3
  (moto) and back.
- A Duck elsewhere reads a managed PostgreSQL listening beyond the machine directly (`verify-full`, the
  certificate in its job), through the Catchment only when it listens on loopback. **[code]**, tested (DuckDB's own
  libpq verifying the self-signed certificate).

## App scaling (added 2026-11-25, branch `records-media`; `plans/app-scaling.md`)

- `[app]`: `instances` (the maximum, 1 to 64), `min_instances` (0), `concurrency` (4: active requests and sockets
  one instance takes), `connections` (PostgreSQL connections one instance may hold; default its concurrency),
  `stop_grace` (10s). `[app.scale]`: `requests` 0.7, `cpu` 0.7, `memory` 0.8, `load` 0.7 (shares), `after` 10s,
  `socket_idle` 5s. **[code]**, tested
- Where: an App with no `[pond] duck` runs every instance on the Catchment. With one (`"M"`, a Pool, dedicated), a
  request finding nothing ready starts an instance on the Catchment when `min_instances = 0` (the quiet App lives
  there), and growth starts instances on the App's compute; `min_instances >= 1` keeps that many there and never
  uses the Catchment (requests wait for the warm one to start). **[code]**, tested with a stand-in launcher
  (subprocesses with their own empty root, through the tunnel). Not yet run on a cloud.
- Instances elsewhere need `state = "none"`, Records they can reach (an external PostgreSQL, or `catchment records
  --listen`), and Media in an object store; otherwise the request answers 503 naming what to change. They read Pond
  data from the data root (a few seconds behind the Catchment's copy), Records over `verify-full`, Media directly.
  **[code]**, tested
- Growth: one instance at a time when, for `after`, active work per ready instance reaches `requests` x
  `concurrency` (active = HTTP requests in flight + WebSockets with a message, either way, within `socket_idle`; an
  idle open tab doesn't count), or CPU (share of its cores), memory (share of `[pond] memory` on the Catchment, of
  the container's limit elsewhere) or the App's reported load pass their thresholds. Shrinking: an instance stops
  after `idle_timeout` without work, never below `min_instances`. **[code]**, tested
- Routing packs: the cookie's instance, else the busiest under `concurrency` and the memory threshold, instances
  elsewhere before the Catchment's, else the least busy. So a Catchment instance empties and idles out once
  instances elsewhere run. **[code]**, tested
- The App's own load: `duckstring.app.report_load(0.9)` or a response header `X-Duckstring-Load: 0.9` (stripped
  before the browser); counts 30 s. The process gets `DUCKSTRING_APP_INSTANCE`, `DUCKSTRING_APP_CONCURRENCY`,
  `DUCKSTRING_APP_CONNECTIONS`; `duckstring.app.records_pool()` is a `psycopg_pool` pool sized to the budget.
  **[code]**, the header tested
- `duckstring app scale APP` shows settings (with their origin: pond.toml, override, default), instances (where,
  active, CPU, memory, load) and recent decisions; `--min --max --concurrency --connections --requests --cpu
  --memory --load` override (kept across redeploys), `--clear` drops them, `--to N [--hold 2h]` sets the count
  (with `--hold`, kept exactly, no idle stops; without, until reached), `--release` drops it. `duckstring app drain
  APP ID`: no new sessions, stops once done (or after 10 minutes of open sockets). Routes `GET|POST
  /api/ponds/{name}/app/scale`, `POST .../app/instances/{id}/drain` (full). **[code]**, tested
- `DUCKSTRING_APP_SCALER=module:Class`: `decide(AppView) -> Decision(desired, drain, reason)`; the Catchment
  enforces min/max, one start at a time, the connection budget and drains. A scaler that raises falls back to the
  default for that pass. **[code]**, tested
- Connections: a managed PostgreSQL's `max_connections` is its memory / 10 MB (50 to 1000); each line's role gets
  `CONNECTION LIMIT` = instances x connections + 2; an App doesn't grow past the server's total less 10.
  **[code]**, the budget unit-tested
- Observability: `app instances` and the bottom panel show where each instance ran and why it started; `/metrics`
  `duckstring_app_instances{place}`, `_app_active`, `_app_cpu_share`, `_app_memory_share`, `_app_reported_load`,
  `_app_at_maximum`, `_app_instance_starts_total{place}`, `_app_instance_stops_total{reason}`; an `app_scale` alert
  kind (each decision; outside `all`); the node shows the count and "max" in amber when held at the maximum.
  **[code]**, tested
- Lifetimes: the agent stops after 5 minutes without its Catchment (`DUCKSTRING_APP_ORPHAN_MINUTES`); a Catchment
  that crashed adopts the instances that dial back; a graceful Catchment shutdown ends them through their
  launchers (an adopted one, which its launcher no longer knows, stops itself 5 minutes later). Instances on Cloud Run
  or Container Apps jobs are replaced an hour before the 7-day limit. **[code]**, adoption tested
